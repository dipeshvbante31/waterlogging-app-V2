How It Works

From a place name to a risk estimate, and what each step can and cannot tell you.

  1. 1. Place or valuesSearch a place, or type weather values yourself.
  2. 2. Weather dataOpen-Meteo geocoding and forecast APIs.
  3. 3. ValidationRanges, units and missing values are checked.
  4. 4. PredictionTrained model if valid, otherwise a labelled fallback.
  5. 5. Risk categoryLow, Moderate or High, with the reasons shown.

The steps in detail

1. Location selection or manual input

On the Live Weather page a place name is turned into coordinates by the Open-Meteo Geocoding API. On the Manual Prediction page you provide the numbers yourself, so no location or network is involved.

2. Historical dataset preparation (offline)

Before the app can use a model, the developer runs scripts/prepare_dataset.py on their own computer. It downloads hourly historical weather and a record of observed street-flooding reports, aligns them in time, and writes a training table. There is no upload feature on this website; training data never passes through it.

3. Weather data retrieval

Live requests ask Open-Meteo for current conditions, the last three days of hourly rain and the next two days of forecast. Every response is labelled live, cached (a recent copy) or stale (older data shown only because the provider failed). If nothing usable exists, the app says so instead of showing made-up values.

4. Feature validation and preprocessing

Values must be in a sensible range, and the rainfall windows must be consistent (rain in the last 3 hours cannot exceed rain in the last 24). Missing values are never silently set to zero. Rainfall is log-transformed (and, for the linear model, scaled) inside the saved pipeline, which was fitted on training rows only.

5. Model training and selection (offline)

scripts/train_model.py compares logistic regression, a random forest and gradient boosting. Models are chosen by macro F1 on forward-chaining time-series validation inside the training period, then scored once on a later, untouched test period. Two simple baselines (always predict the most common class; a single rainfall threshold) are reported next to the model so you can see whether it adds anything.

6. Prediction generation

Both the live page and the manual page call the same prediction service. The trained model is used only when it loads and passes integrity checks, every model input is available, and the location is inside the area it was trained for. Otherwise a transparent heuristic is used. The result always names the method and, for a fallback, the reason.

7. Risk categorisation

The model predicts one of three classes. The fallback computes a 0–100 weather risk index from current rain, forecast rain and rain probability, and maps it to Low, Moderate or High with fixed thresholds. The index is not a probability.

8. Model evaluation

See Model Performance. Figures there are read from files written by the real training run; if no model has been trained, the page says metrics are unavailable. Offline results measure how the model did on past data and do not guarantee real-world accuracy.

9. Limitations, freshness and responsible use

Treat every result as a screening estimate, never as an official warning. Follow local authorities and emergency instructions.

Three different things

Weather forecast
A prediction of rainfall and other weather made by a meteorological model. It says nothing about drains or streets.
Waterlogging risk estimate
This app’s output: how likely conditions are to coincide with reported street flooding, learned from past weather and past reports (or a simple rule when no model applies).
Confirmed waterlogging
An observation that water actually collected somewhere, from a sensor or a report. The app cannot confirm this.

Why rainfall alone is not enough

Heavy rain can fall with no waterlogging, and moderate rain can cause it. The outcome depends on drainage capacity and blockages, terrain and low-lying ground, tides, ground saturation, land cover and local works. Weather alone cannot see most of these.

Training data and where the model applies

The training pipeline in this project is built around two public sources: the Open-Meteo Historical Weather API (hourly reanalysis weather) and the City of New York’s public 311 service-request records, from which street-flooding complaints are counted as the observed outcome. Because those reports exist only for New York City, a model trained from them describes New York City, not Mumbai or anywhere else. The app therefore uses the model only inside its documented coverage area and uses the labelled fallback elsewhere.
